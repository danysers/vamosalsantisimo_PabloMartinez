# Despliegue separado en Dokploy

> El entorno aislado `prueba-rama-oficina` está en preparación; **no** habilita inscripciones ni cobros al público. El SMTP tiene valores no secretos configurados, pero la contraseña permanece fuera del repositorio. No hay credenciales de Mercado Pago en este entorno.

## Arquitectura

- `deploy/dokploy-db.compose.yml`: **stack de PostgreSQL** con volumen persistente, sin puerto público.
- `deploy/dokploy-app.compose.yml`: **stack de aplicación** con migrador, web pública `app`, panel privado `panel` como contenedor independiente y trabajador de correo opcional. Los servicios comparten la red Docker externa indicada por `WORKSHOP_PRIVATE_NETWORK` (predeterminada: `vas_workshop_private`); web y panel se conectan a `dokploy-network` para Traefik. Solo la web pública se conecta además a `PUBLIC_TUNNEL_NETWORK` (predeterminada: `vamosalsantisimo_sites_net`) para el subdominio de prueba; la base, el panel y el trabajador no quedan expuestos allí.
- `compose.yaml`: PostgreSQL **local** para desarrollo, distinto de los dos stacks de producción.

Antes del primer despliegue fuera del entorno de prueba, crear la red privada Docker o configurar el stack DB para crearla, y respaldar PostgreSQL. Configurar ambos Compose en Dokploy como **dos servicios independientes**. Desplegar primero la DB, esperar su healthcheck y recién después la app. En la app, conectar el dominio HTTPS público desde la interfaz de Dokploy al servicio `app`, puerto interno `3000`; no publicar PostgreSQL. `panel` queda bajo el perfil Compose opcional `panel` y **no se inicia ni tiene dominio configurado todavía**. Cuando se decida habilitarlo, definir `PANEL_ORIGIN` como su origen HTTPS, cargar un `BETTER_AUTH_SECRET` estable y activar el perfil `panel`; entonces conectar el futuro dominio solo al servicio `panel`, puerto interno `3000`. Nunca apuntar el dominio del panel al servicio público. La [documentación de dominios Compose de Dokploy](https://docs.dokploy.com/docs/core/docker-compose/domains) explica cómo agrega etiquetas/redes y recomienda comprobar **Preview Compose** antes de desplegar. La [documentación de autodeploy](https://docs.dokploy.com/docs/core/auto-deploy) indica que se habilita para el repositorio y rama seleccionados. No activar despliegue automático de un entorno con inscripciones reales hasta verificar secretos, respaldo/restauración y migraciones allí.

### Entorno aislado de prueba (`rama_oficina`)

En el proyecto existente de Dokploy se creó el entorno **`prueba-rama-oficina`**, separado de `production`, con dos servicios Compose nuevos: **Taller 2026 prueba - PostgreSQL** y **Taller 2026 prueba - web**. Ambos usan el repositorio `danysers/vamosalsantisimo_PabloMartinez`, rama `rama_oficina`, y las rutas `./deploy/dokploy-db.compose.yml` y `./deploy/dokploy-app.compose.yml`. La base tiene autodeploy **desactivado** para no reiniciarse por cada cambio. La web completó un build controlado y tiene autodeploy **activado** para pushes a `rama_oficina`; verificar su funcionamiento con un commit de prueba. Ningún servicio de `production` se editó para probar el taller.

La base de prueba define `WORKSHOP_PRIVATE_NETWORK=vas_workshop_prueba_private` y `WORKSHOP_PRIVATE_NETWORK_EXTERNAL=false` para crear una red propia sin puertos publicados. La web usa la misma red como externa, su propia contraseña PostgreSQL y claves de cifrado **generadas para pruebas** y almacenadas solo en variables privadas de Dokploy. No copiar claves de desarrollo ni producción, ni registrar sus valores en este documento. La imagen de web lleva `DEPLOY_TAG=staging-2026` para evitar usar la etiqueta predeterminada de otros entornos. En la web, `SITE_ORIGIN=https://pruebataller.vamosalsantisimo.com`, `REGISTRATION_EMAIL_READY=0`, sin perfiles `panel` ni `mail` y sin pagos reales. El dominio se asigna al servicio Compose `app`, puerto 3000. Cloudflare tiene una ruta específica para `pruebataller.vamosalsantisimo.com`, antes del comodín, hacia `http://vas-taller-prueba-web-d8zewd-app-1:3000`; el contenedor web debe estar en `vamosalsantisimo_sites_net` para que el túnel pueda alcanzarlo. HTTPS termina en Cloudflare. Las rutas existentes de producción no se modifican.

**Verificado en staging:** PostgreSQL tiene healthcheck correcto, el migrador salió con código 0, el seed creó el catálogo sin abrir inscripciones ni Mercado Pago, la web respondió 200 por HTTPS, `/admin` devolvió 404 en la web pública y `POST /api/taller/inscripciones` devolvió 503 sin guardar una ficha. Confirmar que un commit en `rama_oficina` redepliega solo el servicio web de este entorno y que `production` no se reinicia. Hacer una copia de seguridad y una restauración de ensayo antes de abrir el circuito a participantes.

**Build de bajo impacto:** el Compose construye la imagen una sola vez en `migrate`; `app` y los perfiles opcionales reutilizan la misma etiqueta. El Dockerfile usa una sola descarga de dependencias con `pnpm` (4 solicitudes de red, 1 proceso hijo), caché BuildKit, poda offline de dependencias de desarrollo y un solo trabajador de generación de páginas de Next.js con un heap de 3 GiB. El build de prueba se validó localmente. El segundo build en Dokploy (`3ad8d5b`) terminó en 6m 6s; el túnel siguió disponible, aunque CPU llegó a 100% durante parte de la compilación. Si la carga del host vuelve a crecer o el túnel se desconecta, **cancelar y trasladar la compilación fuera de esa VM**; no repetir despliegues en bucle. En el primer intento anterior, Oracle mostró una carga cercana a 55 sobre 2 vCPU y Dokploy canceló el build.

`DATABASE_URL` de app y panel debe apuntar al nombre DNS `postgres` de la red privada, no a `localhost`; usar la contraseña correspondiente al stack DB. Guardar secretos en el gestor de Dokploy, nunca en Git. `SITE_ORIGIN` pertenece **solo a la web pública**; `PANEL_ORIGIN`/`BETTER_AUTH_URL` pertenece **solo al panel** y debe ser un origen HTTPS distinto. Ambos contenedores usan la misma imagen, pero `APP_SURFACE` impide acceder a rutas administrativas desde la web pública y a páginas públicas desde el panel. Las demás claves requeridas por Compose están documentadas en `docs/configuracion.md`.

La migración se ejecuta antes de iniciar app/worker mediante `scripts/migrate.mjs`; el seed `scripts/seed-workshop.mjs` se ejecuta **una sola vez de manera controlada** después de migrar. Ese seed deja `registration_open=false`, `mercado_pago_enabled=false`, promociones y opciones de acreditación de fondos inactivas. No habilita cobros ni registra asistentes.

## Confirmación por correo oficial

El formulario real `POST /api/taller/inscripciones` guarda la ficha, el pago pendiente o solicitud de ayuda y las tareas de correo **en la misma transacción**: una confirmación al participante y, si pide ayuda, un aviso adicional al organizador. La respuesta idempotente repite la misma referencia, no crea otras tareas. El proceso `scripts/email-worker.mjs` toma la cola y envía desde `contactos@vamosalsantisimo.com`:

- Transferencia: importe, alias `danielservin.mp`, cuenta Mercado Pago, enlace al WhatsApp `3718 63-2884` para adjuntar manualmente el comprobante; indica que el pago continúa pendiente hasta revisión humana.
- Pago en el lugar: importe y estado pendiente hasta registro presencial.
- Inconvenientes para pagar: solicitud pendiente de revisión, sin prometer ingreso automático.
- En una solicitud de ayuda, se encola además un aviso al organizador configurado y se ofrece un enlace para avisarle por WhatsApp; ese enlace no envía el mensaje automáticamente. El panel privado `/admin` permite aprobar o rechazar una solicitud pendiente a un operador vinculado. El correo de decisión al participante se encola solo después de registrar esa revisión.
- Si el estado cambió antes de enviar la confirmación, puede informarse pago confirmado o exención aprobada según la base. La aprobación de ayuda tiene **su propio correo**, encolado solo después de revisar la solicitud. El QR personal se envía **en otro mensaje** y únicamente tras verificación/aprobación.

Los mensajes HTML siguen el modelo negro, dorado y blanco de Vamos al Santísimo, con logo, datos de los coordinadores y redes oficiales, **sin contacto del padre asesor**. El asunto y cuerpo Mercado Pago no anuncian plazos de acreditación. Al crear el servicio Compose de la aplicación en Dokploy:

1. Abrir **Environment / Variables de entorno** del servicio y cargar `SMTP_PASS` con el valor del `.env` local. Usar el campo de secreto si Dokploy lo ofrece. **No** subir el `.env`, copiar la clave al Compose ni incluirla en Git. Los valores `SMTP_HOST`, `SMTP_PORT` y `SMTP_USER` ya tienen valores por defecto en el Compose.
2. Mantener `REGISTRATION_EMAIL_READY=0` y el perfil `mail` desactivado durante el primer despliegue. Verificar que la aplicación y PostgreSQL estén sanos.
3. Para probar el envío, activar `COMPOSE_PROFILES=mail`, confirmar que `email-worker` arranca sin errores y realizar un envío controlado a una casilla de prueba. Confirmar recepción (no basta con ver `queued` en `email_outbox`); revisar fallas y reintentos.
4. Solo después de esa prueba poner `REGISTRATION_EMAIL_READY=1` y, en una operación separada y autorizada, abrir `workshops.registration_open`. Mientras la variable no sea `1`, la API devuelve 503 y **no persiste inscripciones**.

El correo de recordatorios de Mercado Pago se prepara para `danysers@gmail.com`, desde el mismo buzón oficial, pero no se enviará antes de configurar SMTP y opciones reales de acreditación.

El primer administrador se crea de forma interactiva según `docs/configuracion.md` **solo cuando exista el entorno de panel**. Después, en una terminal privada del contenedor `panel`, ejecutar `node scripts/link-admin-operator.mjs --email CORREO_ADMIN --role registration_operator` para previsualizar y repetir con `--apply` para vincularlo. La cuenta local de desarrollo no se copia a la base de producción. La API de decisiones exige sesión Better Auth `admin`, rol operativo habilitado y origen correcto. La aprobación de ayuda y la verificación manual de pago confirman la inscripción, emiten un QR único y encolan el volante por correo en la misma transacción; las decisiones quedan auditadas. `/admin/acreditacion` permite abrir el volante imprimible y leerlo con cámara o lector externo. El escáner está cerrado por defecto: `ADMISSION_SCAN_ENABLED=0`.

No usar pagos reales en pruebas. La ruta pública actual ofrece solo transferencia, pago en el lugar o solicitud de asistencia; Mercado Pago sigue deshabilitado hasta completar órdenes, webhook firmado y conciliación.
